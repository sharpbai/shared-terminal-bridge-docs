# Shared Terminal Bridge（十一）：与 Agent 一起重构，从拆大文件到低成本维护


> **系列导航**：[系列目录](../README.md) · 上一篇：[第十篇：当前架构、性能账本与下一阶段路线图](10-current-architecture-roadmap.md)

记录日期：2026-10-08。本篇复盘 STB 在功能稳定后进行的一轮交互式重构，主要落地提交集中于 2026-09-24。我结合与 Codex 的讨论和 Git 记录，复盘这次重构；这不是逐条聊天转录，也不是一次严格的性能实验。
系列背景：[系列目录](../README.md)。本篇为系列第十一篇，记录功能稳定后如何通过交互式重构降低开发维护成本；原有十篇保留为阶段性历史快照。

## 为什么在功能已经可用之后重构

Shared Terminal Bridge 已经能让人和 Agent 共用真实 tmux：终端事实由 tmux 保存，授权、撤权、任务和审计由本地 Bridge 管理，Codex MCP 与 STB-RDC 作为入口。此时最迫切的问题不再是“能不能执行”，而是“下一次修改，要先理解多少东西”。
快速迭代留下了超长 Python 文件。一次小修改可能要求模型读取大量无关逻辑，人也很难从文件名判断去哪里看。对持续使用 Agent 开发的项目，这种理解成本会在每次新会话里重复支付。
所以我给这次重构设定了明确约束：**功能完全不要调整；改善后续开发时的定位、阅读、修改和验证成本。** 目标不是代码最短，也不是尽可能引入设计模式，而是保持合理的维护和理解成本，让人和模型访问一个小的局部就能有效工作。

## 第一轮反馈：拆小不等于清楚

最初的方向是把单体文件拆开，但看完第一轮拆分后，我提出了一个疑问：

> “这么分依然不知道哪个文件与什么相关。这样分真的能省 token 么？”

这个疑问让我把验收标准从“文件变短”移到了“陌生读者能不能定位”。
机械拆分可能只是把理解成本搬到文件之间。文件虽然短了，如果命名依然抽象、边界依然交叉、依赖依然隐含，模型仍然要读完整个系统，甚至多花一轮查找和拼接上下文。
因此第二轮，我没有让 Codex 立即继续改代码，而是先重新规划：按功能职责划分、说明每个部分负责什么，并预估文件行数。先确认这套结构是否符合我的阅读直觉，再实施。这一步本身就是交互式重构的重要组成部分：**先校准组织方式，再支付实现成本。**

## 第二轮：让目录回答“我想改什么”

最终结构围绕真实维护问题展开，而不是围绕技术技巧展开。

| 想处理的问题 | 主要入口 | 需要理解的边界 |
| --- | --- | --- |
| 终端读取、增量输出和等待观察 | `bridge/observation/service.py` | 读事实，不取得执行权 |
| 租约、generation 和写权限 | `bridge/execution/authority.py` | 过期决策必须在输入 pane 前拒绝 |
| 命令提交与输入 | `bridge/execution/submit.py` | 检查完成后才向真实终端发送 |
| 任务运行、等待和取消 | `bridge/execution/jobs.py`、`job_wait.py` | 任务状态与等待生命周期分别定位 |
| 长任务批准或任务块 | `bridge/execution/long_run.py`、`task_blocks.py` | 审批与编排各有明确责任 |
| MCP 工具定义与工具调用 | `mcp_server/tools/`、`runtime/tool_calls.py` | 协议说明与运行实现分开 |
| stb 命令、参数和中文输出 | `stb_cli/commands_*.py`、`parser_*.py`、`output.py` | 按会话、执行、管理分组 |

这不是要求每个文件只有几十行。把一个完整职责拆碎到很多小文件，也会增加导航成本。合理尺度是：文件承载一个可以命名、可以测试、可以局部修改的责任。
第二次审阅时，我觉得“清晰了不少”，但仍继续追问：还有哪些单体大文件？陌生模型能否快速、省 Token 地上手？这些问题促使重构从目录整理进一步走向开发入口和边界验证。

## 第三轮：入口短，但不能藏起依赖

项目保留 `LocalBridge`、`MinimalMCPServer` 等兼容外观，避免外部调用因为内部搬迁而改变。外观通过显式委托连接职责服务，不依靠多层 Mixin 让行为来源变得难以追踪。
公共 Bridge 方法从 `bridge/protocol/registry.py` 定位，MCP 工具从 `mcp_server/tools/registry.py` 定位。模型不必先读取全部 schema 和实现，先查小索引，再进入相关领域。
只缩短入口仍然不够：如果每个服务能任意访问整个对象，领域边界只是目录上的装饰。因此增加显式服务依赖声明与 `ServiceContext` 约束，并用一致性测试校验。未声明访问不能默默扩散。
这里我接受了一定的结构代码成本，换取依赖可见和错误更早暴露。我的判断标准不是“总代码行数有没有减少”，而是“这次修改需要理解的责任和影响范围有没有缩小”。

## 第四轮：文档也要能局部维护

代码变清楚后，我发现文档依然乱。这让我意识到：如果新模型需要在历史计划、过期说明、验证记录和当前 API 之间来回确认，代码拆分的收益会被文档抵消。
文档重新分为五类：

- `guides/`：如何开始和日常使用。
- `reference/`：当前架构、接口和行为事实。
- `development/`：代码定位、开发约定和测试。
- `validation/`：验证方法、基线和验收证据。
- `history/`：旧设计和阶段性记录，保留历史但不充当当前规范。

README 负责项目背景、用法和导航；`docs/README.md` 负责文档索引。每个主题尽量只有一个当前事实来源，其他位置引用，不复制同一套说明。
`AGENTS.md` 可以使用中文。真正重要的是简短、明确、路径可靠，以及与实际代码一致。它不应该成为另一本架构百科，而是告诉陌生模型：先读哪里、哪些边界不能破坏、修改后如何验证。
我也把一条要求明确下来：**代码结构、测试映射和文档更新属于开发本身，不是功能完成后的可选善后。**

## 第五轮：用检查和 CI 保住结构收益

重构之后，我又从“人和陌生模型的上手成本”出发反复检查，与 Codex 一起修补遗漏。测试也按职责组织，而不是继续堆在少数大文件里。
测试分成不需要真实 tmux 的默认自动测试，以及需要真实终端环境的 `tests/host_tmux/`。后者应在容器外、具备实际 tmux 的主机环境中执行。两类测试验证的事实不同，不能拿一类的通过替代另一类。
进一步增加了协议注册一致性、服务依赖边界、版本一致性等检查，让文件迁移后最容易漂移的关系变成可验证约束。
GitHub CI 首次暴露了 Linux 下初始 tmux 历史配置问题。它随后被修复，而不是把本机通过当作跨平台通过。严格说，这一步已经是重构后的兼容性缺陷修复，不应伪装成“纯文件搬迁”。它说明验证基础设施也是此次实践的一部分。
README 增加 CI 状态和人可读、Agent 低成本维护说明，让使用者能找到验证入口，而不必从会话历史猜测项目质量。

## 可以核对的变化

以主重构提交前的版本与本次记录时的工作树比较，几个兼容入口的物理行数如下。当前工作树基于 `718e9a3`，包含后续维护，因此这不是同一瞬间的严格 A/B 快照。

| 文件 | 主重构前 | 记录时 |
| --- | --- | --- |
| `bridge/local_bridge.py` | 2916 行 | 364 行 |
| `mcp_server/server.py` | 1349 行 | 145 行 |
| `bin/stb` | 733 行 | 29 行 |

这些数字表示入口职责变薄，**不表示功能代码消失，也不代表 Token 按相同比例下降**。领域实现仍然存在，例如记录时 `task_blocks.py` 为 379 行，`jobs.py` 为 349 行。必要时仍要连同相邻依赖一起阅读。
关键提交：

- [4f5b2b8：按局部维护需求重构 STB](https://github.com/sharpbai/shared-terminal-bridge/commit/4f5b2b8)。涉及 114 个文件，8059 行新增、6734 行删除；这是包含搬迁、拆分和测试组织的大规模结构变化，不是净减少代码。
- [4981bf5：增加 CI 与维护边界检查](https://github.com/sharpbai/shared-terminal-bridge/commit/4981bf5)。
- [a6a5625：修复 Linux 初始 tmux 历史配置](https://github.com/sharpbai/shared-terminal-bridge/commit/a6a5625)。
- [f3b193d：说明 CI 与 Agent 友好的维护方式](https://github.com/sharpbai/shared-terminal-bridge/commit/f3b193d)。

这些提交集中于同一天，但不能据此推算整个交互过程只花了几分钟；讨论、审阅和规划时间不等同于提交时间。

## 到底能不能省 Token

从结构变化和我的阅读体验来看，这轮重构有明确改善。但我还没有做同任务、同模型、同环境的维护 Token 对照实验。
合理预期的收益来自三件事：定位入口更小，读取无关实现更少，验证目标更明确。目录不是直接的计费优化器；它降低的是每次修改必须放入上下文的最小必要信息。
也存在反效果：模型无视导航、全库扫描，文档失真，领域服务相互牵连，或者为了追求短文件制造过多跳转，都可能消耗更多上下文。
下一步，我计划用固定维护任务记录：首次正确定位耗时、读取文件数和行数、模型往返次数、输入及非缓存输入 Token、修改范围、回归遗漏。这样才能把“看起来更清楚”推进为“确实降低维护成本”。终端任务的运行 Token 优化与代码维护 Token 优化应分别统计，不能混用以前磁盘检查的数字证明此次重构效果。

## 为什么这是一次有益的交互式实践

对我来说，价值不只在最终目录，而在于我通过持续审阅和反馈，把验收标准变得越来越具体。
我没有把“重构”当成一次笼统授权，而是持续检验产物：文件名能否定位？第一次拆分是否真有收益？陌生模型能否进入局部？文档是否混淆当前与历史？测试是否在正确环境运行？
我与 Codex 一起把这些反馈转化为可执行的结构、路径、规则和检查。我们并没有一次性确定完美架构，而是经历了“提出目标—展示方案—指出理解障碍—重新规划—实现—再检查”的连续校准。
我总结的几条经验：

1. 在拆代码前，先让人看懂职责图和目录命名。
2. 把“我该去哪里改”作为结构验收问题，而不只统计文件长度。
3. 明确功能不变的约束，兼容外观和安全边界不能随整理顺手改变。
4. 把文档、测试和依赖声明一起整理，否则理解成本仍会从别处回来。
5. 用测试维护边界，不依靠模型每次都记住规则。
6. 不宣称尚未测量的 Token 节省；保留基线和可复核证据。
7. 让后续每次功能开发都维护这些入口，避免结构再次退化。

## 一个可复用的简短约定


> 以人和模型能快速定位、理解并局部修改为目标。按明确职责组织代码，使用可读命名和显式依赖，保持文件规模合理。最短代码和设计模式不是目标；合理的维护与理解成本才是目标。修改行为时，同步维护相关测试、结构导航和当前文档，历史记录与现行规范分开保存。

这也是我最希望从 STB 此次重构中保留下来的成果：不是一套必须照搬的目录，而是一种能通过真实阅读反馈不断校准的开发方式。
